## 0. Answers that drive decisions

1. **Ordo cannot express or check architectural rules on code today.** The ECIR contract (`ecir/1`)
   describes requirements, decisions, conflicts, invariants, interfaces, verification obligations and
   cohorts, plus a `dependsOn` DAG between those nodes. It has no node kind for a layer, module,
   dependency rule or tier, and nothing in `ordo ecir check` looks at source code. The nearest things:
   - `ordo boundary assess` [IMPLEMENTED+TESTED] classifies *changed paths* into a declared boundary map
     (globs to layers) and emits advisory signals ORDO-BA-001..010. It is scope and blast-radius
     evidence, not a dependency-rule check. It always exits 0 when it produces an assessment.
   - `DelegationPolicy.ArchitectureConstraints` [IMPLEMENTED+TESTED in core, not reachable from the
     CLI] is an opaque string list copied into delegation packets. The CLI hard-codes it to `[]`
     (`src/Sde.Cli/Ecir.fs:213`), and nothing evaluates it.
   - Generated construction code is tiered Model, then Transition, then Orchestration. Tier order is
     proved by compile-negative `dotnet fsi` probes, but only for code Ordo generates.
2. **The only implemented architecture-dependency check is Dokimos ratchet rule DOK-R008.** It is a
   regex over `.fsproj` `<ProjectReference>` elements, checked against a baseline
   `forbiddenReferences` from/to project map. It works at project granularity only: it cannot see
   module, namespace, type or function dependencies inside a project.
3. **One AST/compiler analyzer exists and can be reused:** `ordo/tools/Ordo.Complexity` uses
   FSharp.Compiler.Service 43.8.400 (`FSharpChecker.ParseFile`, untyped `ParsedInput`, plus
   `FSharpLexer`) and Roslyn (`Microsoft.CodeAnalysis.CSharp` 4.11.0). It is untyped (parse tree only);
   no type-checked or typed-tree walker exists in any repo. Other "import" analysis is line-based
   (`open X` / `using X;` in `ordo/src/Sde.Cli/Boundary.fs:39`, and a hand lexer in Dokimos
   `SourceLexing.fs`).
4. **Inbox document naming:** Praxis enforces no name or front matter. Any file in
   `.praxis/inbox/documents/` except `README.md` and dotfiles is pending
   (`praxis/src/Praxis.Infrastructure/Work/FileInputInbox.fs:64`). The observed convention is
   `YYYY-MM-DD-<ID>-<kebab-slug>.md`, with an H1 `# <ID>: <title>` followed by `Key: value` header
   lines. There is no YAML front matter. See section 5.

### 1.2 ECIR `ecir/1` contract format (from the REL-001 fixtures)

Examples: `research/experiments/REL-001/run-03/fixtures/tasks/V1..V8/contract.json`, `run-02/fixtures/tasks/U1..U9/contract.json`,
`fixtures/d/tasks/T1..T3/contract.json`. They are generated by `run-03/fixtures/make-contracts.py`.

```json
{ "schemaVersion": "ecir/1",
  "sourceManifestDigest": "sha256:<sha256 of the requirement document>",
  "requirements": [ { "source": { "key": "requirements/V1.md#LEDGER-V1-R1", "originalId": "LEDGER-V1-R1",
        "document": "requirements/V1.md", "location": "L18", "revision": "sha256:…", "contentDigest": "sha256:…" },
      "disposition": { "kind": "modeled" },          // modeled | deferred|unresolved|rejected (+reason) | superseded (+reason,targetKey)
      "nodeIds": ["VERIFY-V1-R1", "COHORT-V1"] } ],
  "nodes": [ { "id": "DEC-V7-EMPTY-NOOP", "kind": "decision", "requirementKeys": ["…#LEDGER-V7-R1"],
               "dependsOn": [], "justification": "…" } ] }
```

- Node kinds (`ConstructionIr.fs:36-45`): `decision`, `contract`, `invariant`, `interface`, `cohort`,
  `verificationObligation`, `conflict`, `deferral`, `engineeringRationale`. **There is no
  architecture, layer, module or dependency-rule kind.** `dependsOn` is a DAG between contract nodes,
  not between code units.
- Kinds used across the 20 REL-001 contracts: cohort, verificationObligation, decision, invariant,
  conflict.
- Rules enforced (diagnostic codes are in `ConstructibilityContract.fs:94-136`): exact schema version;
  canonical digest; every modeled requirement maps to nodes reciprocally; each modeled requirement has
  a `verificationObligation` (`MISSING_VERIFICATION`) and a `cohort` (`MISSING_OWNER_COHORT`); no
  duplicate, missing or self dependency; no dependency cycle; a node with no requirement must be a
  justified `engineeringRationale` (`UNJUSTIFIED_NODE`, `ConstructionIr.fs:278-284`); a conflict linked
  from a modeled requirement is refused (`ORDO.CONTRACT.UNRESOLVED_CONFLICT`, `:77`). ecir/1 has no
  in-contract conflict resolution, which is why REL-001 V7 is expected to be refused.

### 1.3 Requirement-to-decision traceability [IMPLEMENTED+TESTED]

- `ConstructibilityContract.RequirementTraceability` (`:36-43`) maps each requirement key to its
  NodeIds, OwnerCohortIds, DecisionIds, ConflictIds and VerificationObligationIds. The success output
  `ordo.constructibility-identity/1` (`:328`, encoder `:413-421`) lists `contractDigest`,
  `requirementKeys`, `decisionIds` and `conflictIds`.
- Readiness mode (REL-GATE-002, `assessPinnedReadiness` `:474`, `ordo.constructibility-readiness/1`
  `:439`) takes `--requirement KEY…` and `--authorized-decision ID…`. It reports `requiredDecisionIds`,
  and refuses when a required decision is not authorized (`MISSING_DECISION_AUTHORIZATION`) or an
  authorization is outside scope.
- Traceability stops at verification obligations (ids). **Nothing traces a requirement or decision to
  source files, modules or code symbols.**

### 1.5 Boundary amplification (`ordo boundary assess`) [IMPLEMENTED+TESTED]

- Core: `src/Ordo.Core/BoundaryAmplification.fs` (803 lines). Wire: `BoundaryAmplificationWire.fs`.
  Adapter: `src/Sde.Cli/Boundary.fs`. Tests: `tests/Ordo.Tests/BoundaryAmplificationTests.fs` (41
  facts), `tests/Sde.Core.Tests/BoundaryCommandTests.fs` (6). Fixtures:
  `tests/fixtures/boundary-amplification/`.
- Inputs:
  - `ordo.boundary-map/1`: boundaries `{id, layer, patterns[]}`, where the first matching glob wins.
    Layers: cli, application, domain, persistence, provider, rendering, infrastructure, tests,
    documentation, build, or a custom name. Also `indicators[{boundary, imports[]}]` and
    `orchestration[]` globs.
  - `ordo.boundary-expectation/1`: `{workItem, requirement, expectedBoundaries[]}`.
  - `ordo.changed-files/1`: `files[{path, changeCount, imports[]}]`.
  - optional policy file.
- Imports are taken from the changed-files document or, with `--root`, read from disk with a
  line-prefix scan of `open X` / `using X;` (`Boundary.fs:36-60,75-95`). This is not AST-based.
- Signals ORDO-BA-001..010 (`BoundaryAmplification.fs:237-254`), for example 001 (unexpected
  boundary), 004 (crosses ≥N core layers), 009 (writes outside the declared write set). The risk
  level and decomposition advice are **advisory**: "gating is the consumer's decision".
- **It does not check dependency direction** (that A must not reference B). It answers which
  boundaries a change touched against which it was expected to touch.

### 1.6 CLI: exact syntax, exit codes and output

The binary is named `ordo` in the native release and keeps `sde` as a compatibility alias
(`release/echelon.release-input.json:4-8`). The assembly name is `sde`
(`src/Sde.Cli/Sde.Cli.fsproj:10`). Usage text is in `src/Sde.Cli/Args.fs:107,112,164`:

```
ordo ecir check --blueprint FILE [--expected-digest sha256:HEX] [--requirement KEY]... [--authorized-decision ID]... [--json]
ordo ecir validate --manifest FILE --blueprint FILE [--cohort ID] [--json]
ordo ecir scaffold --manifest FILE --output FILE [--json]
ordo ecir recognize --manifest FILE --blueprint FILE --cohort ID [--decisions FILE] [--approvals FILE] [--pin FILE]
                    [--allow GLOB]... [--escalate-open-questions] [--packets DIR] [--json]
ordo boundary assess --map FILE --expected FILE --changed FILE [--policy FILE] [--root DIR] [--json]
ordo init|status|verify|upgrade|doctor ...   (SDE install lifecycle)
```

There is **no `ordo check` verb**; the verb is `ordo ecir check`. The REL-001 harness invocation
(`run-03/harness/setup.sh:82`) is:
`"$ORDO" ecir check --blueprint "$HI/contract.json" --json > out.json; rc=$?`, then
`jq -r .contractDigest out.json`.

- Exit codes (`src/Sde.Core/Lifecycle.fs:20-40`): 0 success or admitted; 1 refused or failed; 2
  invalid arguments; 3/4 Node-launcher only; 5 `--check` drift; 6 `boundary assess` invalid input.
  For `ecir check`: 0 admitted or ready, 1 refused (`Ecir.fs:120-125`).
- `ecir check --json` output: on success, `ordo.constructibility-identity/1`
  (`{schemaVersion, contractSchemaVersion, contractDigest, requirementKeys, decisionIds, conflictIds}`),
  or `ordo.constructibility-readiness/1` in readiness mode. On refusal,
  `ordo.constructibility-diagnostics/1` `{diagnostics:[{code, subject, message}]}` on stdout with exit 1.
  Without `--json`, a human line goes to stdout, and on refusal `Contract refused:\n<diagnostics json>`
  goes to stderr.

### 2.3 Completion gating, attestation and the trust root (REL-GATE-003/004)

Status: `.ros/work/queue.md:233-235` marks REL-GATE-003, REL-GATE-004 and REL-GATE-004-LOCATOR
`complete`. They are present in v3.19.0. Docs: `docs/verified-completion-rollout.md`.

- `ros.json` `workProtocol` flags: `requireVerifiedCompletion` (implies attestation unless
  `allowUnattestedEvidence`), `requireAttestedEvidence`, and `trustedVerifierKeyIds`
  (`["sha256:<hex SPKI>"]`). Read at `src/Praxis.Infrastructure/Work/FileWorkClaims.fs:251-330`.
- **Protected policy (REL-GATE-004)** (`src/Praxis.Application/Work/ProtectedCompletionPolicy.fs`):
  the worktree `ros.json` must be no weaker than `ros.json` at the merge base with the protected
  branch. The branch is located from `refs/remotes/origin/HEAD`, else `origin/main`; failures give
  `PRX.COMPLETION.POLICY_CHANGED` / `POLICY_UNAVAILABLE`. When attestation is required, the authority
  must name only keys pinned in protected `trustedVerifierKeyIds` (`:87-107,165-177`). An authority file
  inside the worktree or `.git` gives `PRX.COMPLETION.UNTRUSTED_AUTHORITY`. A keyless authority gives
  `PRX.COMPLETION.ATTESTATION_REQUIRED`. Tested in `tests/Praxis.Tests/AttestedCompletionTests.fs`.
- **Evidence bound to the exact commit:** the verifier engine (`TrustedVerifier.fs:231-363`) re-reads
  the claim, does `git clone --no-hardlinks` and a detached checkout of the *exact commit*
  (`:254-266,331`), and enforces `protectedPaths` sha256 at that commit (`ProtectedPathCode`, `:347`).
  It runs each policy validation as argv with no shell and a timeout, then signs one
  `echelon.verification-receipt/1` per validation as DSSE v1, ECDSA P-256. The key lives in process
  memory (`:15-17`). `work verify` refuses a dirty worktree, untracked files included (`:438-443`).
  Receipts are stored as `<generation>-<commit12>-<receiptId>.json` (`:447`).
- Verifier policy `echelon.validation-policy/1` (intake `TrustedVerifier.fs:73-119`), example from
  `run-03/harness/setup.sh:89-92`:
  ```json
  {"schemaVersion":"echelon.validation-policy/1","policyId":"rel003-V1",
   "validations":[{"name":"unit-tests","evidenceId":"EV-TESTS","command":["/abs/dotnet","test","Ledger.slnx"],"timeoutSeconds":900}],
   "protectedPaths":[{"path":"tests/Ledger.Tests/Acceptance/V1AcceptanceTests.fs","sha256":"<hex>"}]}
  ```
  The `verifier serve` startup line is `{keyId, publicKey, policyDigest}`. The host copies it into the
  authority's `TrustedVerifierKeys` and `ValidationPolicyDigest` (`setup.sh:93-101`).
- **How the gate invokes Dokimos** (`FileWorkClaims.fs:14-27,83`): as a separate process,
  `dokimos completion verify --packet <praxis.completion-packet/1> --authority <dokimos.completion-authority/1>`.
  The executable is `$PRAXIS_DOKIMOS_EXECUTABLE`, else `dokimos` on PATH (a `.dll` runs via `dotnet`).
  Absence, a crash, a timeout or an unparsable receipt all fail closed.
- Agent environment for the assured protocol (`setup.sh:120-125`): `PRAXIS_ACTOR_KIND=agent`,
  `PRAXIS_ACTOR=…`, `PRAXIS_DOKIMOS_EXECUTABLE`, `PRAXIS_VERIFIER_SOCKET`,
  `PRAXIS_COMPLETION_AUTHORITY` (host file outside the repo), `PRAXIS_ORDO_CONTRACT`.
- Harness sequence (`run-03/harness/briefs/workflow-d.md`):
  ```
  praxis work claim --id ITEM --token TOKEN --lease-seconds 3600
  git add -A && git commit -m "ITEM: ..."
  praxis work verify --id ITEM --token TOKEN            # host verifier runs tests at HEAD, returns signed receipts
  praxis work complete-verified --id ITEM --token TOKEN # exit 0 verified, 3 refused, 2 usage, 1 storage
  ```
- **Gap for ARCH-001:** a verifier validation is any argv command. An architecture checker can be
  attached today as one more policy `validations[]` entry, and becomes attested evidence bound to the
  commit, **with no Praxis code change**. This holds as long as the checker and its rule file live
  outside the agent-writable tree, or are pinned through `protectedPaths`.

### 3.3 Policy format, receipts and tamper resistance

- Quality policy: `config/dokimos-policy.json` (schema 1.2.0: `requiredEvidence`,
  `ratchets[{metricId, bestAccepted, preference, disposition}]`, `thresholds`,
  `unavailableBehavior`).
- Completion authority `dokimos.completion-authority/1` (`CompletionVerification.fs:~73-100`):
  WorkItemId, ClaimToken, FencingGeneration, ExpectedCommit, ExpectedVerificationRevision,
  SupportedOrdoContractVersions, ExpectedOrdoContractDigest, Required{Requirement,Decision,ConflictResolution,ValidationName}Ids,
  Evidence observations (digest, revision, status, optional DSSE attestation), ConsumedPacketDigests
  (replay), lease window, EvaluatedAt (Dokimos never reads the clock), TrustedVerifierKeys,
  ValidationPolicyDigest.
- Tamper model: the agent's packet is "only a claim". Every expectation comes from the host
  authority. In attested mode, evidence must carry a signature from a host-pinned key over the exact
  payload bytes, bound to the commit. **Dokimos does not sign its own receipt.** The receipt is plain
  JSON plus an exit code, so its integrity rests on the host running Dokimos. The trust root is the
  authority file, which Praxis REL-GATE-004 now requires to be outside the worktree and pinned by
  protected policy.
