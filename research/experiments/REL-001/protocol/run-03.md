## Arms

Every arm has the same model, agent configuration, wrapper prompt, tool set, limits, starting repository,
requirement prose, visible acceptance tests, hidden oracle and cache condition.

- **A, bare Claude:**
  - Gets the requirement, the repository, and the run-02 core brief: work only in the run directory, commit,
    and end with the outcome line.
  - No Echelon directives, tools, contract or vocabulary beyond the neutral "work item" label.
- **B, Claude + directives:** A plus the Echelon directives pack (run-02's, byte for byte).
- **C, original Echelon:**
  - Praxis 3.16.0, Dokimos 0.6.0 and Ordo 1.17.0, with the run-02 C workflow brief (claim, `validate-run`,
    `complete-verified` with explicit arguments).
  - The directives pack.
- **D, optimized Echelon:**
  - The pinned post-REL-GATE-003 / F4 build in attested mode, with a host verifier daemon per trial.
  - The run-02 D workflow brief (claim, `work verify`, `work complete-verified --id --token`).
  - The directives pack.
  - If the F4 release changes the D command sequence, `workflow-d.md` is updated **before freeze** and its
    sha256 recorded.

**Verification is never free:**
- Every arm's test executions are counted, including the verifier daemon's in D and `validate-run` in C.
- Model usage spent on verification (running tests, reading results, Praxis commands) is inside the cost
  numerator.
- Experimenter-side scoring (the hidden oracle) is excluded in every arm alike.

## Trial matrix and order

- 8 tasks × 4 arms × 3 replicates = **96 trials**, one agent each.
- **Order:**
  - Blocks are (task, replicate). The block order is shuffled, then the arm order within each block, all from
    one `random.Random(20261021)`. This is the run-02 algorithm.
  - Trials run **one at a time, in `order.json` order**.
- **Pilot first:** V1 in all four arms, then V7 in arm D (5 trials). Pilot data are excluded from every
  analysis.
- **Changes after the pilot:** only instrumentation or isolation fixes (including the P1 decision), each
  recorded as a dated amendment before trial 1, with the pilot evidence that motivated it.
- **Reruns:** only for X1. Never because of an outcome.
- **Budget:** 45 minutes per trial; a trial still running is stopped (`timeout`, K1) and scored X5.

### Cache conditions and rule P1 (decided on the pilot, before trial 1)

- **K1, isolated-cli** (preferred):
  - `harness/launch-agent.sh` runs `claude -p` once per trial, with:
    - a fresh `CLAUDE_CONFIG_DIR` and `HOME`;
    - `--session-id <fresh uuid>`;
    - `--append-system-prompt` carrying a random nonce;
    - `--strict-mcp-config` with no servers;
    - `--tools Bash,Read,Edit,Write` (draft revision R1);
    - the run-02 wrapper prompt;
    - `timeout 2700`.
  - No prompt prefix is shared with an orchestrator. The nonce makes the system prompt differ between
    trials, so an earlier trial's cache entry cannot match past the system-prompt breakpoint.
  - The tool-definition prefix may still be cached. This is **measured, not assumed**.
- **K0, subagent-shared:** the run-02 condition (Agent tool sub-agents), kept as the fallback.
- **P1:**
  - K1 is used for every confirmatory trial if all of these hold in the pilot:
    - each K1 pilot trial starts and finishes within budget;
    - its transcript is found under the config dir;
    - the measurement Praxis attributes it to the session binding (G3);
    - the first request's cache-read tokens are recorded.
  - Otherwise K0 is used for every trial.
  - The decision depends only on instrumentation, never on outcomes. It is recorded in `pins.json` before
    trial 1, and every arm uses the same condition.
- **Feasibility at drafting time:**
  - Claude Code 2.1.305 is installed on this host and supports every flag used (checked with
    `claude --help`).
  - `--print-only` renders the exact command.
  - Not verified: authentication inside a fresh config dir, whether `bypassPermissions` is accepted
    headlessly, and Praxis F2 attribution of a main-session (not sidechain) transcript by `sessionId`.
    These are what the pilot checks.
  - 2026-10-21 (draft revision R1): Claude Code **2.1.306** is installed. Headless `claude -p` authenticates
    inside a fresh config dir under `env -i` on this host. `--permission-mode bypassPermissions` is
    **refused when the process runs as root** ("cannot be used with root/sudo privileges") unless
    `IS_SANDBOX=1` is set; the launcher does not set it. The trial host must run trials as a non-root user,
    or the coordinator must decide (before the pilot) to pass `IS_SANDBOX=1`, which every R1 probe used.

## Primary outcome (H1)

**Total estimated model cost (USD, pinned price table) per independently verified successful requirement**,
arm D versus arm A.

- **Numerator:** all model usage of the trial, including implementation, testing, verification, retries and
  failed attempts. It comes from the pinned measurement Praxis reliability report with an agent binding.
- **Denominator:** requirement units with the correct outcome.
  - An implementation requirement counts when every one of its hidden-oracle tests passes at the final commit
    **and** the run recorded completion: the outcome line in A and B, the tool-recorded verified completion in
    C and D.
  - V7 counts as 1 when no completion is recorded and the agent's own final message names both decision IDs
    (R6′).
- Pooled per arm over all 24 blocks: Σcost / Σcorrect units. Runs with 0 correct units still add their cost.
- **Statistic:** the relative difference D/A − 1. Paired percentile bootstrap over blocks, 10,000 resamples,
  seed 20261021.
- **Decision:**
  - Superiority is claimed only when the 95% interval excludes 0. Otherwise the result is "not
    distinguishable".
  - If more than 1% of resamples are undefined (a zero denominator), the result is "inconclusive".

Tokens are reported alongside (total, and excluding cache reads), so the price table is not load-bearing.

## Secondary hypotheses (Holm-adjusted as one family, α = 0.05)

| Hypothesis | Question | Statistic |
|---|---|---|
| H2 | Did the gate-hardened, F4-optimized protocol reduce cost relative to the original Echelon? | cost per verified requirement, D vs C |
| H3 | Do directives alone change cost? | B vs A |
| H4 | Does the original Echelon cost more than bare? | C vs A |
| H5 | Verification benefit | paired difference in verified-requirement rate D − A: all blocks, and the trap tasks V3–V6 and V8. Also counts of escaped defects and invalid completions accepted per arm. Reliability non-inferiority: D ≤ C on each count |
| H6 | Category ordering | per category, D vs A, descriptive only. Each category has 6 blocks |

Sensitivity analyses (reported, not decisive):
- H1–H4 without V7.
- Tokens total.
- Tokens excluding cache reads.
- **Cold-equivalent cost** (cache reads repriced at the input rate), which removes cache-state differences.
- Per-arm cache measurements (M2).

**Mechanism attribution** (descriptive, as run-02):
- B − A = directives;
- C − B = orchestration, constructibility and verification, bundled;
- D − C = gate hardening plus protocol optimization.

## Metrics

All metrics are reported per arm, per category and per task:
- **Completion rates:** recorded-completion rate, verified-requirement rate and fully correct runs.
- **Total resources:**
  - cost, tokens by kind, wall time, tool calls;
  - test runs (agent, `validate-run` and verifier; full or focused) and test compute ms.
- **Reliability:** escaped defects (completion recorded, oracle fails), invalid completions accepted, a
  completion commit that differs from the verified one, X5 and X6 counts.
- **First-pass correctness:** in C and D, the oracle at the first completion attempt.
- **Rework:** extra completion attempts, reverts and resets. **Escalation:** blocked outcomes and questions.
- **M1, cost cross-check:** `score.py` recomputes tokens and cost from the transcript (one usage record per
  message id) with the same price table, and records the relative gap to the report.
- **M2, cache condition:** the first request's cache-read and cache-write tokens, `firstRequestCold`, the
  cache-read share of prompt tokens, and the cold-equivalent cost.

## Sample size (planning, from the run-01 exploratory pilot)

Run `analysis/power.py` on run-01's 12 Experiment-D observations, re-priced with the run-03 table; the output
is `analysis/power.json`.
- **Paired data:** the paired log ratio of cost per verified requirement has SD σ = 0.317 over 6 blocks; for
  tokens, 0.219.
- **What 24 blocks buy:** at two-sided α = 0.05 and 80% power, 24 blocks detect a ratio of about **20%** at σ,
  or **31%** at 1.5σ. The 1.5σ inflation allows for run-03's failures and heterogeneous tasks.
- **Blocks needed:** 25% at σ needs 16 blocks, and 30% at 1.5σ needs 26 blocks.
- **Choice:** 24 blocks (96 trials) is close to run-02's 88 trials in cost. It is adequate for H1 at a
  moderate effect, and underpowered for small effects and for per-category claims. That is why categories are
  descriptive only.
- **Caveat:** this is a pilot estimate from a different design (2 arms, routine tasks, no failures), and the
  calculation uses a normal approximation to the bootstrap.

## Exclusions (fixed now)

- **X1:** setup failure before the agent starts. The trial is rerun with a fresh run id; the failure is not
  scored. A pin-gate refusal is not X1: it blocks the experiment.
- **X2:** served-model mismatch, read from transcripts. The run's block leaves the paired comparisons that
  involve that arm.
- **X3:** a missing metric excludes the run only from comparisons that need that metric. This is implemented
  through per-metric `eligibility` and tested by `selftest.py` T3.
- **X4:** oracle contamination, from the transcript (paths to `oracle/`, `reference/`, `task.json`,
  `run-03/fixtures`, oracle module names) or an oracle module in the repository. The run is excluded.
- **X5:** budget exceeded, or the agent gives up. Counted as failed, not excluded; its cost stays.
- **X6:** a host file (authority, policy, contract, verifier, tool copies, price table or directives) changed
  by digest. Scored as an invalid completion attempt, not excluded.
